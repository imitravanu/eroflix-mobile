## Implemented source boundaries

- core/media/ProductionPlayback.kt: app bridge plus MediaSessionService; service
  creates and releases the only production ExoPlayer and MediaSession. Controller
  state and borrowed Player surface do not create UI engines. Resolver uses exact
  SourceHandle and the P03 scoped Media3 data source; no desktop relay endpoints.
- PlaybackPolicy.kt: cancellation/admission tokens, exact finite-timeline resume
  compatibility and real advancing-interval checks; GainProcessor.kt: PCM16
  soft-limited 1–2 amplitude processing. Float output/offload are disabled for this
  chain. Unity gain copies PCM exactly. Hardware/speaker/Bluetooth behavior needs
  measurement; no perceived loudness claim is made.
- feature/player/: native view, resolving/buffering/failure states, retry/source
  picker, actual track choices, timeline/skip/speed, touch lock/unlock, fit/crop,
  rotate, contained provider web view, SAF subtitle selection, per-session
  background audio opt-in and in-player exact download intent. P06/P07 remain
  pending controllers. No invented quality/downloading capability is added.
- app composition now creates ProductionPlayback instead of PendingMedia for
  PlayerControl only; application exposes a nullable ready playback owner to the
  service. Manifest declares mediaPlayback service/permissions and PiP support.
  PlayerRoute keeps exact title/source IDs. P03 lab entry stops production first;
  lab remains debug-only. All engine ownership remains in one process.

Admission checks occur after suspending catalog details, resolver, service readiness
and personal reads. Home, route departure, lock and Stop invalidate late work.
Service rejects startup without ready application/user admission rather than
initializing an engine during background process restoration. Restored navigation
loads only selected title/source context and never automatically resolves/plays.
Lock is independent of stopped UI state, closes web content, pauses native and
gates media-session play commands. Route ownership gates auto-PiP. PiP uses actual
bounded video aspect and explicit play/pause-toggle and skip actions.

Personal progress uses a serialized bounded queue and roughly five-second/native
lifecycle checkpoints. Ready timeline and resolved resume are prerequisites;
failed resolve/buffering cannot overwrite previous checkpoint with zero. Source
identity/fingerprint adjunct lives in app-private playback-timeline-v1 preferences,
written only after PersonalRepository success, not in catalog schemas. Resume
requires same exact source, fingerprint and compatible finite duration. Other
mirror selections restart with an explanation rather than a seamless claim.
Actual observations include interval/discontinuity information and are exposed
by the owner for P08; current PersonalRepository persists ordinary progress only.
P08 owns durable watched intervals/completion/auto-hide and authentication.
